# 빈 경전 — 앞으로의 방향 (plan.md)

작성: 2026-10-06 · 기준: main `b3d26d2`(0.1.0, 테스트 358개 통과, 배포 200)
이 문서는 "무엇을 어떤 순서로, 왜 하는가"만 정한다. 세부 구현 계획은 단계를 시작할 때 `docs/superpowers/plans/`에 따로 쓴다.

## 0. 지금 어디에 있나

- 코드로는 M0–M6이 끝났다(마을 8개, 봉인 서고, 빈 경전 8쪽, 에필로그, 일과, PWA, 한/영).
- 하지만 **아무도 브라우저에서 플레이하거나 소리를 들어 보지 않았다.** 테스트가 통과한다는 것과 "재미있고 쓸 만하다"는 다른 문제다.
- M1 완료 기준 9번(사용자 플레이 판정)이 비어 있다. 계획·인계 문서는 이 판정 전에 M2 계획을 쓰지 말라고 했지만 M2–M6이 판정 없이 진행됐다. 그 대가로 지금 방향 결정이 한꺼번에 몰려 있다.
- 전체 검토에서 Critical 1건·Important 13건을 찾아 고쳤다. 같은 종류의 결함(화면 연결, 옛 저장 파일, 시간대별 막힘)은 **자동 테스트가 못 잡았다**는 점이 교훈이다.

## 1. 원칙

1. **사람의 판정이 먼저다.** 새 기능보다 플레이 확인이 앞선다. 판정 전에는 범위를 넓히지 않는다.
2. **고치기 전에 재현한다.** 버그는 실패하는 테스트나 실제 콘텐츠 탐침으로 먼저 보인다.
3. **독립 검토를 건너뛰지 않는다.** 구현자와 검토자를 분리하고, 마일스톤마다 전체 검토를 돌린다.
4. **한계는 숨기지 않는다.** 못 한 것은 README와 인계 문서에 사실대로 적는다.

## 2. 단계

### 단계 A — 플레이 확인과 판정 (사용자 필요, 최우선)
목표: 지금 배포본이 즐길 만한지 사람이 판정한다.
- 사용자가 배포본(https://taejinkim7-dev.github.io/hollow-codex/)으로 칼라스를 두 갈래 모두 끝까지 플레이한다. PC와 휴대폰 모두.
- 확인할 것: 타일 그림이 뜻과 맞는지, 음악·효과음이 들을 만한지, 메뉴 저장·불러오기·새 게임, 전투 터치, 에필로그 표시, 추론이 막히지 않는지, 45분 안팎인지.
- 산출물: `docs/handoff.md`에 판정(계속 / 방향 수정 / 중단)과 발견한 문제 목록.
- 종료 조건: 판정이 기록된다. "방향 수정"이면 단계 C 전에 계획을 다시 쓴다.

### 단계 B — 안전망 보강 (에이전트가 바로 할 수 있음)
목표: 사람이 눈으로만 확인할 수 있던 부분을 자동 테스트가 지키게 한다. 단계 A와 병행 가능.
1. **화면 연결 테스트**: 메뉴(저장·불러오기·새 게임), 열석 이동, 에필로그, 전투 터치를 jsdom 또는 Playwright로 한 번씩 검증. 지금은 이 부분에 테스트가 없다.
2. **플레이 스모크 e2e**: 새 게임 → 칼라스 도착 → 대화 한 번 → 저장 → 새로고침 → 이어하기. e2e는 최소로(`docs/TESTING_POLICY.md`).
3. **옛 저장 파일 회귀 고정**: 이번에 만든 v1/v2/v3 실제 모양 저장 파일을 테스트 fixture로 저장소에 남긴다.
4. **미뤄 둔 사소한 결함**: 금지어 검사의 camelCase 복합어·`-ies` 복수형, 정답을 풀어 쓴 일부 소문 문구(용맹·헤론), `arrivalCell`의 고리 칸 NPC 검사, 멈춘 `indexedDB.open`, 모듈 로드 시 만들어지는 `AudioContext`, 알 수 없는 YAML 키 거부.
5. **npm audit 개발 도구 취약점 6건** 조사(배포 번들에는 없음). 의존성 갱신이 안전하면 갱신.
6. **정식 상표 조사 계획**: 공개 전 필요 여부를 정한다(현재는 검색만 했음).
- 종료 조건: 위 1–3이 통과하고 게이트가 그대로 초록이다.

### 단계 C — 스펙과의 차이 메우기 (판정 뒤 범위를 정함)
스펙(`docs/superpowers/specs/2026-10-06-hollow-codex-design.md`)에 있지만 0.1.0에 없는 것. 우선순위 순.
1. **열석 고리 단서 대화**: `fact.ring.*`를 알려 주는 NPC 대화를 쓴다. 지금은 고리 사이 이동이 실제로는 열리지 않는다(spec §3.3-4). 작고 효과가 크다.
2. **능력 6개 구현과 능력 화면**: 용맹(전투 버티기), 연민(설득해 물리기) 등 spec §4.3. 능력 목록 화면도 없다.
3. **마을 위기 풀이가 에필로그에 반영**: 지금은 마지막 장에서 고른 단어만 반영된다(spec §3.3-5, §4.4).
4. **동료 7명**: 마을마다 한 명(spec §4.6). 콘텐츠 작업량이 가장 크다. 마을 하나씩 나눠 진행.
5. **틀린 경전 단어 안내**: 지금은 틀려도 아무 일도 없다.
- 각 항목은 시작 전에 짧은 설계(무엇이 달라지는지)를 사용자에게 보여 주고 승인받는다.
- 종료 조건: spec §4의 각 시스템이 "있다 / 의도적으로 뺐다(문서에 이유)" 중 하나가 된다.

### 단계 D — 콘텐츠와 균형
- 단계 A의 플레이 기록에 따라 대사·힌트·난이도(hp·공격력·추론 단서 수) 조정.
- 타일 번호·음악 편곡을 사람의 눈·귀로 확인해 교정.
- 8개 마을의 분량을 실제 플레이 시간으로 확인(목표 6~10시간).

### 단계 E — 공개 준비
- 이름·상표 정식 확인, 라이선스 장부 최종 점검(`check:content` 통과로 충분하지 않은 부분은 사람이 훑어보기), 크레딧 화면 검토.
- 접근성 점검(키보드만으로 진행, 화면 낭독기 읽기 순서).
- Google Drive 동기화는 계속 미룬다(승인된 차이 3). 필요해지면 새 OAuth 클라이언트와 개인정보·약관 페이지를 함께 만든다.

## 3. 사용자가 정해 줄 것

| 결정 | 선택지 | 추천 |
|---|---|---|
| M1 판정 | 계속 / 방향 수정 / 중단 | 단계 A 결과로 |
| 0.1.0의 범위 | 지금 상태를 "미리보기"로 공개 / 단계 C까지 하고 공개 | 지금 상태는 비공개 유지, 단계 C-1·C-3까지 하고 공개 |
| 동료 7명과 능력 6개 | 이번에 만든다 / 0.2.0으로 미룬다 | 0.2.0으로 미루고 한계로 명시 |
| 자율 진행 범위 | 에이전트가 단계 B를 바로 진행 / 단계마다 확인 | 단계 B는 바로, 단계 C부터 확인 |

## 4. 작업 방식 (다음 세션에서)

- 시작: `AGENTS.md` → 이 문서 → `docs/handoff.md` 마지막 절 → 진행 중 계획.
- 단계마다: 계획서 → 서브에이전트 구현 → Task별 검토 → 게이트(Haiku) → main merge·push → 배포 확인 → 인계 문서 갱신.
- 마일스톤이 끝나면 **전체 검토**를 반드시 돌린다(이번에 이 검토가 Critical 결함을 찾았다).
- 한 번에 너무 멀리 가지 않는다: 단계 사이에서 사용자 판정이 필요한 곳은 문서에 표시하고 멈춘다.
